# 캐시 설계

값을 캐시에 넣기 전에 결정할 사항을 설명합니다. 캐시할 대상, 키 구성, 유효 시간, 정합성 유지 방법을 다룹니다. 이 규칙은 `CacheService`와 어노테이션에 똑같이 적용됩니다.

## 캐시할 대상

| 캐시할 값 | 캐시하지 않을 값 |
|---|---|
| 자주 읽고 드물게 바뀌는 값: 코드, 설정, 라벨, 권한 집합 | 읽을 때마다 바뀌는 값: 카운터, 잔액, 재고 |
| 만드는 비용이 큰 값: 여러 테이블의 조인, 다른 서비스 호출 | 읽는 비용이 낮은 값: 이미 데이터베이스 캐시에 있는 테이블의 기본 키 조회 |
| 여러 호출자에게 같은 값 | 호출자마다 다르고 다시 조회하는 일이 드문 값 |

## 캐시 이름과 키

- 값의 종류마다 `authors`, `author-names`처럼 캐시 이름을 따로 지정하세요. 이름 하나가 유효 시간, 통계, `clear`의 단위입니다.
- 값이 의존하는 모든 요소로 키를 구성하세요. 언어에 따라 달라지는 라벨은 `ko:a1`처럼 언어를 키에 포함합니다.
- 키는 짧고 읽기 쉽게 구성하세요. 키는 모든 항목과 함께 저장되고 로그와 Redis에 표시됩니다.
- 개인 정보를 키에 넣지 마세요. 키는 `getKeys`와 저장소 도구로 조회됩니다.

## 유효 시간 선택

| 값의 종류 | 유효 시간 | 이유 |
|---|---|---|
| 배포나 관리자 작업으로 바뀌는 코드와 라벨 | 수 시간 | 오래된 값이 문제를 일으키지 않고 변경이 드뭅니다 |
| 사용자가 수정하는 레코드 | 수 분. 쓸 때마다 교체하거나 제거합니다 | 정합성은 제거로 유지하고, 유효 시간은 제거가 누락된 경우의 한도 역할만 합니다 |
| 다른 서비스의 결과 | 해당 서비스가 허용하는 시간 | 데이터의 소유자가 허용 가능한 지연 범위를 결정합니다 |
| 인증 번호 같은 일회용 값 | 값의 유효 시간(초 또는 분) | 값을 캐시에만 보관합니다. 값이 만료되면 항목도 없어져야 합니다 |

로컬 저장소에서는 캐시 이름이 처음 생성된 호출의 유효 시간을 계속 사용하므로, 유효 시간마다 캐시 이름을 따로 지정하세요. 저장소별 규칙은 [저장소 선택](./choosing-a-store.md)에 있습니다.

## 정합성 유지

- 데이터를 변경하는 메서드에서 쓰기가 성공한 뒤에 캐시를 변경하세요. 새 값을 `put`하거나, `evict`한 뒤 다음 조회에서 다시 불러옵니다.
- 캐시한 값이 여러 레코드로 구성된다면 갱신하지 말고 제거하세요. 다음 조회에서 다시 구성하는 편이 부분 수정보다 단순합니다.
- 롤백되는 트랜잭션에서 쓰기를 실행하면 캐시 항목이 데이터베이스보다 앞선 상태로 남습니다. 이 차이가 문제가 된다면 `@TransactionalEventListener` 등을 사용해 커밋 후에 캐시를 변경하세요.
- 인스턴스가 여러 개라면 공유 저장소를 사용하세요. 로컬 저장소에서는 인스턴스마다 사본이 따로 있어, 한 인스턴스의 제거가 다른 인스턴스에 반영되지 않습니다.

## 시작 시 캐시 채우기

```java
@Component
@RequiredArgsConstructor
public class GenreCacheWarmer implements ApplicationRunner {

    private final GenreRepository repository;
    private final CacheService cache;

    @Override
    public void run(ApplicationArguments args) {
        Map<Object, String> labels = repository.findAll().stream()
            .collect(Collectors.toMap(Genre::getCode, Genre::getName));
        cache.putAll("genres", labels, Duration.ofHours(6));
    }
}
```

모든 요청에 필요한 작고 완결된 집합만 미리 채우세요. 조회하면서 채워지는 캐시는 미리 채울 필요가 없습니다.

## 효과 확인

하루 정도 사용한 뒤 `getStatistics(cacheName)`을 확인하세요. 적중률이 0에 가까우면 키가 지나치게 세분화되어 있거나 항목이 다시 조회되기 전에 만료된다는 뜻입니다. 크기가 계속 늘어나는 캐시는 키가 반복되지 않는다는 뜻입니다. [캐시 모니터링](./monitoring-the-cache.md)을 참고하세요.
